## 1. What EVE is

EVE is a cross-platform (Linux and Windows) desktop application for producing **short promotional videos**
— trailers, teasers, clips for YouTube, YouTube Shorts, Instagram Reels and TikTok — from raw gameplay
recordings.

The primary use case: the owner records gameplay sessions of his racing game (*V-Core*), loads the
recordings into EVE, adjusts a few settings and launches an AI agent. The agent analyses the footage,
finds the best moments, edits a trailer and shows the result as an editable timeline with a live preview.
The user can correct any step before the final render.

EVE must also work:
- with **any AI provider** (Anthropic, OpenAI, local models via Ollama / LM Studio, …);
- in **Auto mode** (rule-based heuristics, no AI, offline, free);
- in **Manual mode** (no automation at all; the user does everything by hand).

EVE is a generic editor: nothing in it is specific to V-Core or to racing games.

### Non-goals (for now)
- Not a general-purpose NLE (no multicam, no colour grading, no keyframe animation editor, no plugins).
- No external event/telemetry logs as input (see §7.6 for the extension point kept for later).
- No cloud service, no accounts, no telemetry. Everything runs locally except calls to the AI provider
  the user configures.

## 2. Glossary

| Term | Meaning |
|---|---|
| **Project** | A folder (`<name>.eve/`) containing `project.json`, caches, proxies and exports. |
| **Clip** | A source video file imported into the project. Never modified. |
| **Source view** | The view of a clip with its player, thumbnail strip, waveform and **zone lanes**. |
| **Zone** | A time range on a clip. Three kinds: **Exclude (red)**, **Candidate (blue)**, **Highlight (yellow)**. |
| **Edit timeline** | The assembled output video: segments, transitions, text, music, logo, end card. |
| **Phase** | One of the three automated steps: 1 Analysis → blue, 2 Refinement → yellow, 3 Assembly → edit timeline. |
| **Command** | An atomic, undoable operation on the project. Both the UI and the AI only change the project through commands. |
| **Provider** | An AI backend reached through an adapter (Anthropic, OpenAI-compatible, …). |
| **Brand kit** | Reusable assets: logo, game title, call-to-action text, fonts, colours, music library. |
| **Output preset** | A target format (aspect ratio, resolution, fps, codec, max duration, reframing mode). |

## 3. User workflow

1. **New project** → give it a name → import one or more clips (drag & drop or file dialog).
   EVE probes each clip (ffprobe), generates proxies, thumbnails and a waveform in the background.
2. **Settings panel**: output presets (e.g. YouTube 16:9 + Shorts 9:16), target duration, mood/pace
   (e.g. "adrenaline", "cinematic"), music track(s), brand kit, AI provider/model, optional free-text prompt.
3. **(Optional) Mark red zones** — parts that must never appear in the result.
4. **Run Phase 1** (AI, Auto, or skip and draw blue zones by hand). Blue zones appear on the timeline.
5. **Review / edit blue zones**. Then **run Phase 2** → yellow zones appear.
6. **Review / edit yellow zones**. Then **run Phase 3** → the edit timeline is built.
7. **Preview** instantly, tweak by hand or ask the agent for targeted changes
   ("the intro is too slow", "put the jump earlier").
8. **Render** final videos for every selected output preset.

A **"Run all phases"** button chains 1 → 2 → 3 without stopping. Every phase can also be run alone,
re-run, or skipped because the user did it manually.

While an AI phase runs, an **Agent activity panel** shows what the agent is doing in plain English
("Analysing clip 2 of 3", "Selected 00:42.1–00:47.3: tight corner at high speed"), and the timeline
updates live as zones/segments are created.

## 4. Zones

### 4.1 Lanes and colours
In the source view each clip has three lanes, top to bottom:

| Lane | Colour | Who creates it | Purpose |
|---|---|---|---|
| Exclude | **Red** | **User only** | Footage that must never be analysed or used. |
| Candidate | **Light blue** | Phase 1 (AI/Auto) or user | Rough "interesting" regions. |
| Highlight | **Yellow** | Phase 2 (AI/Auto) or user | Precisely trimmed best moments, ready for assembly. |

### 4.2 Zone data
Every zone stores: `id`, `kind`, `clip_id`, `start_us`, `end_us` (integer microseconds, never floats),
`origin` (`user` | `ai` | `auto`), `locked` (bool), `score` (0–1, optional), `priority` (1–3 stars, optional),
`label` (short English description, editable), `parent_id` (yellow → originating blue, optional),
`stale` (bool).

### 4.3 Editing (user)
- Create by click-dragging on a lane; resize by dragging edges; move by dragging the body; delete with `Del`.
- Mark-in / mark-out while playing (`I` / `O`), then create a zone of the chosen kind from the marked range
  (`R` red, `B` blue, `Y` yellow).
- Edit label and priority in an inspector panel.
- Snapping to frame boundaries always; optional snapping to scene cuts and to other zones' edges.
- Any zone **created or modified by the user becomes `locked`**. The user can unlock it explicitly.

### 4.4 Rules (enforced in code, never only in prompts)
1. **Red zones are absolute.**
   - Only the user can create, modify or delete them. AI tools have no access to red-zone mutations.
   - Phase 1 does not analyse red ranges at all.
   - Phases 2 and 3 can never produce zones/segments overlapping red ranges.
   - Creating or extending a red zone over existing blue/yellow zones **trims** them, or **splits** them
     in two when the red range falls in the middle — even if they are locked. EVE notifies the user.
   - Transitions must not consume frames from red zones (transition "handles" count as used frames).
     Handles are centred on the cut: a crossfade of duration *d* uses *d*/2 of extra output time
     (converted to source time with the segment speed) after the outgoing segment and before the
     incoming one. Dips and flashes do not blend shots and need no handles.
   - Blue/yellow zones and edit-timeline segments never overlap red ranges, whoever creates them
     (the user included): such commands are rejected. When a red zone is created or extended, segments
     using those frames are trimmed, split or removed as well (and marked stale), and crossfades whose
     handles would need red frames become cuts.
   - Red exclusion applies to both the video and the original audio of the clip (added music is unaffected).
2. **Locked zones** are never changed or deleted by AI/Auto. Re-running a phase keeps them and works around them.
3. **Yellow vs blue**: a yellow zone may extend beyond its blue parent by at most the configurable
   tolerance (default ±2.0 s). One blue zone may yield several yellow zones.
4. **Staleness**: editing a blue zone marks its yellow children `stale`; editing a yellow zone marks the
   edit-timeline segments that use it `stale`. Stale items are highlighted and the user can regenerate
   only the affected items ("Refresh stale") instead of re-running a whole phase.
5. **Final validation before render** (blocking): no output frame may come from a red range; every
   segment must reference existing media; durations must respect the output preset. On failure, export is
   refused and the offending items are shown and selectable.

## 5. The three phases

All phases can run in **AI** mode (via the configured provider) or **Auto** mode (heuristics, §5.4).
Both modes produce their results exclusively through commands (§7.3), so results are undoable.

### 5.1 Phase 1 — Preliminary analysis → blue zones
Two-step analysis, skipping red ranges:
1. **Numeric pass over the whole clip** (fast, local, cached per clip):
   - scene cuts (histogram distance between consecutive downscaled frames);
   - motion intensity per time window (frame differencing on downscaled frames) and the motion
     centroid, which also drives follow-crop reframing;
   - audio energy, peaks and onsets (librosa);
   - result: a time series of features (10 values per second) and a ranked list of candidate windows.
   Frames are decoded by ffmpeg at 64×36 grey and processed with numpy, so OpenCV and PySceneDetect
   are not needed. Features are cached per clip content; red ranges are masked out before scoring,
   so they are never scored, selected or sent to an AI.
2. **AI review** (AI mode only): for the top candidate windows, EVE sends the model a compact summary of
   features plus a small number of **downscaled frames** (JPEG, e.g. 512 px wide) if the model supports
   vision. The model creates blue zones with `score` and `label`.
   If the model has no vision, it works only on the numeric features.

Limits are configurable: max candidate windows, max frames per window, max total frames per run.

### 5.2 Phase 2 — Refinement → yellow zones
Only inside blue zones (minus red ranges):
- dense analysis (more frames per second, finer feature resolution);
- find the peak moment(s) and choose precise in/out points that respect the **shot rhythm**:
  - if music is selected: snap shot lengths and cut points to the beat grid (beat detection on the music);
  - otherwise: use the preset's default shot-length range (shorter for vertical/social, longer for YouTube);
- may split one blue into several yellows; may extend up to the tolerance;
- sets `score`, `label`, suggested `priority`, `parent_id`.

### 5.3 Phase 3 — Assembly → edit timeline
Uses only yellow zones (non-stale preferred; warn on stale):
- pick zones to fit the target duration, using priority then score;
- order them with a trailer structure: hook (strongest shot in the first 1–2 s for social formats),
  build-up, climax, end card;
- apply speed changes (slow motion on peaks, slight speed-ups on build-up), transitions (cut, dip to
  black/white, crossfade, flash), text overlays, title card, logo, call-to-action end card, music with
  fades, game-audio mixing/ducking under music, loudness normalisation;
- produce one edit timeline per **aspect-ratio family** when reframing changes the composition
  (16:9 and 9:16 may need different shot choices/crops); presets of the same family share a timeline.
- Re-running Phase 3 rebuilds the segments of those timelines and removes texts it added; texts added by
  the user, music and end-card settings are kept. Like every phase run, it is one undo step.

### 5.4 Auto mode (no AI)
Deterministic heuristics using the same numeric features:
- Phase 1: score = weighted sum of normalised motion, audio energy and scene-change density; take the top
  windows above a threshold, merge neighbours, respect min/max lengths.
- Phase 2: inside each blue, find the highest-scoring sub-window of a rhythm-compliant length, snap to beats.
- Phase 3: template-based assembly (fixed structure per mood), ordered by score with an escalating curve:
  strongest shot first (hook), build-up by rising score, second strongest last (climax). Moods:
  *adrenaline* (cuts, slight speed-up on the build-up, flash and slow motion on the climax), *epic*
  (dip to black and slow motion on the climax), *cinematic* (crossfades). Vertical/4:5 timelines use
  shots 20% shorter. With music, shot lengths are whole beats and the music starts on its first beat.
Auto mode is the reference baseline and the fallback when no provider is configured.

### 5.5 Targeted follow-up requests
After Phase 3, the user can type a request in the agent panel. The agent receives the current project
state and the same tools, and must make **minimal changes** (only what the request requires).

## 6. Edit timeline and preview

### 6.1 Edit timeline content
- **Video segments**: source clip, in/out (µs), speed (constant, or a simple ramp approximated by
  sub-segments), crop/reframe parameters, transition into the next segment.
- **Overlays**: text items (title, captions, call-to-action) with a small set of styles; logo/watermark.
- **Audio**: music track(s) with in/out, volume, fades; game-audio level per segment; global loudness target.
- **End card**: logo + CTA text + optional background.
- The user can edit everything by hand: reorder, trim, change speed/transition, edit text, swap music.

### 6.2 Preview (two levels)
1. **Instant preview**: plays the cut list with mpv using an EDL (segments of proxy files played in
   sequence, no rendering). Text/logo overlays are drawn by the Qt layer on top of the player as an
   approximation. Updates immediately on every change.
2. **Draft render**: a low-resolution, full-fidelity render (transitions, speed, overlays, audio mix) made
   with ffmpeg from proxies in the background, debounced after changes, cancellable. Shown with a
   "draft" badge. Drafts render at one third of the preset size with single-pass loudness
   normalisation; final renders use two-pass `loudnorm`.

### 6.3 Output presets (initial set)
| Preset | Aspect | Resolution | Notes |
|---|---|---|---|
| YouTube | 16:9 | 1920×1080 (option 2560×1440, 3840×2160) | H.264 high profile, AAC |
| Shorts / Reels / TikTok | 9:16 | 1080×1920 | reframing required |
| Instagram feed | 4:5 | 1080×1350 | reframing required |

- Frame rate: user-selectable (30/60), source footage conformed to it (sources may be VFR).
- **Reframing modes** for vertical/4:5: centre crop; **follow crop** (crop window follows the motion centroid,
  smoothed); **blurred background** (full frame fitted in the middle, blurred zoomed copy behind).
  A segment's `center_x`/`center_y` move the crop window by hand. Follow crop needs the motion path
  produced by analysis (M5); without it, it behaves like a centre crop.
- Text sizes are fractions of the short side of the output and shrink so that the longest line fits
  90% of the width. Text styles: `title`, `caption`, `cta`. Their appearance comes from the project's
  **text look**, chosen by the user: `classic` (default: white outlined title, caption on a dark box,
  call to action on an accent box), `band` (accent title on a dark full-width band, shadowed
  left-aligned caption, outlined accent call to action) or `bold` (large title with an accent shadow,
  left-aligned caption on an accent bar, call to action on an accent box). The accent is the brand
  kit's primary colour.
- Default transition: cut. Crossfades, dips and flashes are chosen per segment.
- Platform duration limits change over time: store them as editable preset values, never hardcode
  assumptions elsewhere in the code.
- Loudness target default −14 LUFS integrated (ffmpeg `loudnorm`, two-pass), editable.

## 7. Architecture

### 7.1 Layers
```
ui  (PySide6)            ──► uses everything below; no business logic
cli (eve command)        ──► headless access to core/media/analysis/ai
mcp (MCP server)         ──► exposes the tool registry to external MCP clients
ai  (providers, agent)   ──► talks to models; only acts through the tool registry
analysis                 ──► numeric features, scoring, Auto-mode heuristics
media                    ──► ffprobe, proxies, thumbnails, waveforms, render graph → ffmpeg
core                     ──► project model, zones, edit timeline, commands, undo/redo, validation, persistence
```
- `core`, `media`, `analysis` and `ai` **must not import Qt**. Long operations report progress through a
  callback/progress protocol and accept a cancellation token.
- Platform-specific code lives behind small interfaces with Linux and Windows implementations.

### 7.2 Project format
```
MyTrailer.eve/
├── project.json        # model, versioned with "schema_version"; migrations kept in code
├── cache/              # analysis features per clip (keyed by file fingerprint)
├── proxies/            # low-res CFR proxies (e.g. 540p)
├── thumbs/             # thumbnail strips, waveforms
└── exports/            # final renders
```
- Clips are referenced by absolute path plus a fingerprint (size + mtime + hash of sampled chunks);
  missing/moved files are detected and the user can relink them.
- `project.json` is written atomically (write temp file → rename). Autosave + crash-safe backups.
- Model classes use pydantic (validation + JSON Schema export).

### 7.3 Commands
Every mutation is a command (`AddClip`, `RemoveClip`, `CreateZone`, `UpdateZone`, `DeleteZone`,
`LockZone`, `AddSegment`, `UpdateSegment`, `MoveSegment`, `RemoveSegment`, `SetTransition`, `AddText`,
`UpdateText`, `SetMusic`, `SetOutputPresets`, …). Commands:
- validate against the rules in §4.4 (including red-zone and lock rules) and reject invalid operations
  with a clear error message (which is returned to the AI as a tool error);
- are grouped into transactions (one AI phase run = one undo step, plus finer steps inside it);
- record `origin` (user / ai / auto) and are listed in a history panel;
- some are user-only regardless of the caller: clip import/removal, project settings and output presets,
  zone lock/unlock, and every red-zone mutation.

### 7.4 Tool registry
A single registry defines every tool once with a JSON Schema for its arguments. The same definitions are
used by the AI adapters, the MCP server and the CLI. Tools fall into two groups:
- **Read/analysis**: `get_project_state`, `get_clip_info`, `get_features(clip, range, resolution)`,
  `get_frames(clip, timestamps, width)`, `get_beats(music)`, `get_zones(kind)`, `get_timeline`.
- **Mutation**: thin wrappers over commands.
Each phase exposes only the tools it needs (e.g. Phase 1 can create/update/delete unlocked blue zones but
cannot touch yellow zones or the edit timeline). Red-zone mutation tools do not exist for the AI at all.

### 7.5 AI layer
- **Claude Code provider (default)**: many users have a Claude subscription but no API account. EVE runs
  the user's own Claude Code headless (`claude -p … --output-format stream-json`) with every built-in
  tool disabled (`--tools ""`), only EVE's MCP server attached (`--strict-mcp-config`, restricted to the
  current phase's tools via `eve mcp --phase`) and no saved session. The MCP server edits and saves
  `project.json`; the GUI follows the file live (§11). Usage counts against the user's Claude plan; no
  API key is involved. Claude Code is installed and logged in once by the user (`eve doctor` and Help →
  System check show the steps).
  EVE starts Claude Code with `MCP_CONNECTION_NONBLOCKING=false` (and a long `MCP_TIMEOUT`) so the
  model never starts before EVE's tools are connected; a run that ends without any EVE tool call is
  reported as an error (nothing was changed), never as success.
- **Provider adapters** behind one interface for the in-process agent loop: `AnthropicProvider`
  (optional, API key), `OpenAICompatibleProvider` (M7: OpenAI, Ollama, LM Studio, llama.cpp server and
  other compatible endpoints), `GeminiProvider` (later). Tests use `FakeProvider`.
- **Capabilities** per model profile: tool calling, vision, max images per request, context size.
  EVE adapts: no vision → numeric-only analysis; no tool calling → provider not selectable for phases.
- **Agent loop**: phase-specific system prompt + tools; max steps; per-run token/cost accounting when the
  provider reports usage; cancellation; every tool call and result is logged to the activity panel and
  the log file.
- **Privacy**: never upload whole videos. Only downscaled frames and numeric summaries leave the machine.
- **Secrets**: API keys are stored in the OS keyring (`keyring`), never in `project.json`, settings files
  or logs.
- Prompts live in versioned text files under `src/.../ai/prompts/`, in English.

### 7.6 Extension point: additional clip metadata
Define (but do not implement beyond a no-op) a `ClipMetadataSource` interface: given a clip, it may return
extra time-stamped information that analysis and the AI can use. It exists so that game event logs can
be added later without changing the analysis pipeline. Do not implement any log format now.

### 7.7 Render engine
The edit timeline is compiled into an intermediate **render graph** (inputs, trims, speed, crops, overlays,
transitions, audio mix), which is then translated into an ffmpeg command (`-filter_complex` script file
for long graphs). This separation keeps the ffmpeg string generation testable (golden tests on the
generated graph/arguments). All subprocesses are called with argument lists (never `shell=True`), their
stdout/stderr and exit code are captured to the log, and progress is parsed from `-progress`.

## 8. UI

### 8.1 Main window
- **Media bin** (left): project clips with thumbnails, durations, status (proxy ready, analysed).
- **Player** (centre): mpv via `python-mpv`, toggle between *Source*, *Edit timeline* (instant preview)
  and *Draft* playback. EVE uses libmpv's software render API into a Qt widget (no native window
  embedding, no shared OpenGL context), so it works on X11, Wayland and Windows and overlays are plain
  Qt painting. Without libmpv the player shows how to install it and everything else keeps working.
- **Source view** (below player): thumbnail strip, waveform, red/blue/yellow lanes, playhead.
- **Edit timeline** (bottom): video segments, overlay track, music track.
- **Right panel tabs**: Settings, Inspector (selected zone/segment/text), Agent activity + prompt box,
  History.
- **Log console**: toggled with `F12`, always available, shows all application logs and external process
  output, with "copy" and "export" buttons.

### 8.2 Interaction rules
- Every operation that is not instantaneous shows an **activity indicator**; operations that may take
  more than ~10 seconds also show a **progress bar** with ETA when possible, and are **cancellable**.
- Background jobs (proxies, analysis, draft renders, AI runs) appear in a job list.
- The UI never blocks: heavy work runs in worker threads/processes.
- Keyboard: `Space` play/pause, `J`/`K`/`L` shuttle, `←`/`→` frame step, `I`/`O` mark in/out,
  `R`/`B`/`Y` create zone from marks, `Del` delete, `Ctrl+Z`/`Ctrl+Shift+Z` undo/redo, `F12` log console,
  `A` add the marked range to the edit timeline, `T` add text, `Ctrl+I` import, `Ctrl+E` export,
  `Ctrl+D` render draft.
- UI strings are English and wrapped for translation (Qt translation system), so other languages can be
  added later.
- Light and dark themes following the system.

## 9. Settings

- **Application settings** (stored with `platformdirs` in the user config dir): ffmpeg/ffprobe/libmpv paths
  (auto-detected), proxy resolution, cache size limit, AI provider profiles (provider, endpoint, model,
  capabilities; keys in keyring), defaults for new projects.
- **Project settings**: output presets, target duration, mood/pace, yellow tolerance, shot-length range,
  music, brand kit selection, transition style, text look, reframing mode, loudness target, game-audio
  level.
- **Brand kits** (reusable across projects): logo (PNG/SVG), game title, CTA text, fonts, colours, music
  library folder. Bundle at least one open-licence font (OFL) so text rendering works out of the box
  (EVE bundles *Anton*). The renderer reads PNG/JPEG logos; SVG logos are rasterised to PNG when they are
  added to a brand kit.
  The brand kit editor shows an **end card preview** for each default output preset (16:9, 9:16, 4:5):
  one still from the middle of the card, rendered in the background with the same render graph and
  ffmpeg as an export (debounced after each edit), using the open project's text look. A project's
  end card can still override the call to action and the background.

## 10. CLI

An `eve` command exposing headless operations (used for automation and for testing without a display):
```
eve doctor                          # check ffmpeg, ffprobe, libmpv, GPU encoders, keyring
eve new <dir> --name <name>
eve import <project> <clip>...
eve relink <project> [--search <dir>]...  # find moved source files by content
eve analyze  <project> [--mode ai|auto] [--provider claude_code|anthropic]  # Phase 1
eve refine   <project> [--mode ai|auto]     # Phase 2
eve assemble <project> [--mode ai|auto]     # Phase 3
eve refresh  <project> [--mode ai|auto]     # regenerate stale items only
eve ask      <project> "<request>"          # targeted follow-up request (AI, §5.5)
eve mcp --project <project> [--phase …]     # MCP server (§11)
eve render   <project> [--preset ...] [--draft]
eve validate <project>
```

## 11. MCP server

`eve mcp --project <path>` starts an MCP server (stdio) exposing the tool registry (§7.4), so external MCP
clients (e.g. Claude Desktop, Claude Code) can drive a project. The same rule enforcement applies.
If the GUI has the same project open, it reloads on external changes (file watcher + project revision
number); conflicting concurrent edits are rejected with a clear error.

`--phase analyze|refine|assemble|followup` limits the exposed tools (default `followup`: all editing
tools); `--frame-budget` caps the frames a client may view. Every tool call reloads the project if it
changed on disk and saves it atomically after a change.

While EVE's own AI run is in progress (M6), the GUI polls `project.json`, shows each saved state, pauses
local editing and undo, and records the whole run as one undo step (origin `ai`). Reloading on changes
made by *other* clients while the user is also editing, and conflict handling, are M8.

## 12. Logging and errors

- Structured logging to a rotating file in the user log dir and to the in-app console.
- Every external process: full command line, stdout/stderr, exit code, duration.
- Every AI call: provider, model, tool calls, token usage (never API keys, never full base64 images).
- User-facing errors are short and actionable; details are one click away (link to the log entry).

## 13. Technology stack

- **Python 3.12**, managed with **uv**; `pyproject.toml` with `hatchling`.
- **PySide6** (Qt 6) for the GUI, **python-mpv** for playback.
- **ffmpeg / ffprobe** (external binaries) for probing, proxies and rendering.
- **numpy** and **librosa** (which brings **soundfile**) for analysis. OpenCV and PySceneDetect were
  planned but are not needed: video features are computed with numpy on frames decoded by ffmpeg.
- **pydantic** for the model, **platformdirs**, **keyring**.
- **anthropic** and **openai** SDKs for providers; the official **mcp** Python SDK for the MCP server.
- Dev: **pytest**, **pytest-qt**, **ruff** (lint + format), **mypy** (strict on `core`, `media`, `analysis`, `ai`).
- Package name: `easy_video_editor`; console scripts: `eve` (CLI) and `eve-gui` (GUI).
- Every new dependency must be justified in the commit message and checked for licence compatibility.

### External binaries
Discovery order: path set in settings → binaries bundled with the release → system `PATH`.
- Linux: ffmpeg and libmpv from the system package manager in development; bundled in the AppImage.
- Windows: `ffmpeg.exe`, `ffprobe.exe` and `libmpv-2.dll` bundled in the release.
`eve doctor` and a first-run "System check" dialog report what is missing with copy-pasteable fix commands
per platform (Fedora, Ubuntu/Debian, Arch, Windows).

## 15. Testing strategy

- **Unit**: model validation, every command (including red-zone trimming/splitting, lock rules, tolerance,
  staleness propagation), undo/redo, project persistence and migrations, render-graph compilation
  (golden tests on generated ffmpeg arguments), Auto-mode heuristics on synthetic feature series.
- **Integration**: generate tiny synthetic clips with ffmpeg (`-f lavfi -i testsrc2`, `sine` audio, short
  durations) at test time; run import → proxies → analysis → assembly → render; verify output with ffprobe
  (duration, resolution, streams) and verify that no frame comes from red ranges (encode a visible frame
  counter in synthetic clips and check sampled output frames).
- **AI**: a `FakeProvider` replays scripted tool calls; tests cover the agent loop, tool errors, phase tool
  restrictions and cancellation. No real API calls in CI.
- **GUI**: smoke tests with `pytest-qt` and `QT_QPA_PLATFORM=offscreen` (window opens, project loads,
  zone creation via commands updates the lanes). mpv-dependent tests are skipped when libmpv is missing.
- CI runs on Linux and Windows. Tests needing ffmpeg install it in the workflow.

## 17. Distribution

- Source code on GitHub; binaries **only** in GitHub Releases (never committed).
- Versioning: SemVer, tags `vX.Y.Z`; `CHANGELOG.md` in *Keep a Changelog* format; release notes generated
  from the changelog section.
- Release assets: `EVE-<version>-windows-x64.zip`, `EVE-<version>-x86_64.AppImage`, `SHA256SUMS`.
  The folder holds `eve` (command line, also the MCP server Claude Code starts) and `eve-gui` (the
  editor); FFmpeg/FFprobe go in `bin/`. The Windows zip bundles `libmpv-2.dll`; the AppImage uses the
  system libmpv (bundling it would pull in a whole desktop stack) and runs the command-line program
  with `cli` as its first argument. Builds come from `.github/workflows/release.yml`, which smoke-tests
  the packaged programs (doctor, Auto pipeline, draft render, GUI start-up) before publishing.
- Pre-releases (`v0.1.0-alpha.N`) may be published before M9 so the owner can test on real machines.
- Publishing is automatic: a commit on `main` whose `__version__` has no tag yet is built, tested
  and published, and its tag is created (`0.1.0a3` → `v0.1.0-alpha.3`; `.devN` versions are never
  released). To release, bump `__version__` and add the matching `CHANGELOG.md` section in the same
  commit. A `v*` tag pushed by hand, or a run of *Release* from the Actions tab with a tag name, also
  publishes; the tag must match `__version__` (PEP 440 comparison).
- README has a prominent "Download" section pointing to the latest release, plus build-from-source steps.

## Appendix A — `CLAUDE.md`

```markdown
# CLAUDE.md — working rules for EVE

Read `docs/SPEC.md` before any change. It is the source of truth; update it in the same commit when a
design decision changes.

## Non-negotiable rules
1. Everything is in English: code, identifiers, comments, docstrings, commit messages, docs, UI strings,
   log messages, prompts, issues and release notes.
2. All project mutations go through commands (`core/commands`). Never mutate the model directly from UI,
   AI or CLI code.
3. Red-zone and lock rules (SPEC §4.4) are enforced in `core`, covered by tests, and never relaxed.
   The AI has no tool that can create, modify or delete red zones.
4. `core`, `media`, `analysis` and `ai` never import Qt.
5. External processes: argument lists only, never `shell=True`; capture stdout/stderr/exit code to the log.
6. Paths via `pathlib`; no hardcoded separators; remember Linux is case-sensitive.
7. Times are integer microseconds in the model; convert only at boundaries.
8. No secrets in the repo, in project files, in settings files or in logs. API keys live in the OS keyring.
9. No real AI API calls in tests; use `FakeProvider`.
10. Non-instant operations show an activity indicator; operations that may exceed ~10 s show a progress bar
    and are cancellable. The UI thread never blocks.
11. Never commit binaries, generated media, proxies or caches.

## Workflow
- Follow the milestone plan in `docs/SPEC.md` §16, one milestone at a time.
- Small, focused commits using Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`,
  `build:`, `ci:`, `chore:`).
- Before moving on: `uv run ruff check`, `uv run ruff format --check`, `uv run mypy`, `uv run pytest` all green.
- Add an entry to `CHANGELOG.md` under "Unreleased" for user-visible changes.
- Justify every new dependency in the commit message and check its licence.

## Useful commands
uv sync
uv run pytest
uv run ruff check . && uv run ruff format --check .
uv run mypy
uv run eve doctor
QT_QPA_PLATFORM=offscreen uv run pytest tests/gui
```
